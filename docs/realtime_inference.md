# Real-Time Recovery Inference Layer

## Overview
This stage establishes the real-time inference/service layer but does not provide persistent production event storage, real payment execution, or production deployment. It provides a synchronous pipeline processing ONE incoming failed-payment event through the existing machine learning and decisioning foundation.

## Event Contract
The incoming event is expected to be a JSON-compatible dictionary matching the `DataValidator` schema.
Required fields:
- `payment_amount` (float)
- `failure_reason` (string, must be supported)
- `payment_method` (string, must be supported)
- `is_subscription` (0 or 1)
- `customer_tenure_months` (float)
- `past_successful_payments` (int)
- `past_failed_payments` (int)
- `historical_success_rate` (float)
- `time_since_last_success_days` (float)
- `days_overdue` (float)
- `recovery_attempts_so_far` (int)

Optional fields:
- `payment_id`: Preserved if supplied. If not supplied, a request-scoped UUID is generated. This UUID is NOT a persistent idempotency key, and this stage does NOT implement persistent deduplication.
- `customer_id`: Preserved in the event identity response.

## Validation
Data is strictly validated against `DataValidator`. Any invalid input (e.g., negative amounts, NaNs, invalid categories) will be cleanly rejected, returning a structured error response with status `error` without triggering ML prediction. Validation errors continue returning the existing `DataValidator` error messages.

## Exception Handling
Pipeline exceptions return a safe public error message (`Inference pipeline failed. Please retry or inspect server logs.`) with `error_type` set to `pipeline_exception`, preventing raw internal exception details from being exposed to clients.

## Model Prediction & Decision Integration
If the event is valid, the `RecoveryEngine` executes the model inference and assigns a probability and rule-based priority/action. The `DecisionTracer` evaluates economic impacts and attaches an explanation.

## Returned Response
The `predict_event` method returns a structured dictionary:
```json
{
  "event_identity": {"payment_id": "...", "customer_id": "..."},
  "validation": {"is_valid": true, "errors": []},
  "prediction": {"recovery_probability": 0.85},
  "decision": {"recommended_action": "Retry Payment", "recovery_priority": "HIGH"},
  "economic_estimate": {"expected_recovery": 4250.0, "effective_retry_cost": 50.0, "expected_retry_net_value": 4200.0},
  "explanation": {"decision_reason": "...", "key_input_factors": [...]},
  "audit_record": {"audit_id": "...", "...": "..."},
  "processing_metadata": {"status": "success", "processing_time_ms": 12.5, "timestamp_utc": "..."}
}
```

## Audit and Idempotency Architecture
The architecture flows as follows:
Incoming event → validation → prediction → decision → explanation → transient audit record → returned in response

The audit record generated by Stage 15 is:
- in-memory
- returned as part of the response
- not persisted by the inference service
- not an idempotency store

Persistent audit history and persistent idempotency belong to a future persistence stage.

## Limitations
- **Synthetic Data**: Predictions are based on models trained on synthetic data.
- **No Persistence**: Idempotency and audit records are transient/returned in the payload. No database is configured.
- **No Real Payments**: The engine recommends actions but does not trigger external Razorpay APIs.
